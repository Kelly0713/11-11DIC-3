### **Abstract（摘要）**

* **A. Attention Getter (Motivation 動機與引題)**：氣象預報與空氣品質監測資料豐富，民眾在規劃日常活動時高度依賴這些開放數據，需求已從單純「查詢環境資訊」轉向「知道出門前該做何準備」。
* **B. But (However 挑戰)**：環境資料分散於中央氣象署與環境部等不同平台，使用者需自行切換查詢；通用型預報未整合個人偏好與活動情境，且未適當揭露預報不確定性，增添使用者判讀負擔。
* **C. Cure (解藥)**：提出 **AirGuard AI（個人化天氣助理 AI Agent 系統）**，整合多源環境資料與個人偏好，針對使用者規劃的多站行程提供具備情境相關性與可追溯性的行前建議。
* **D. Development (方法設計)**：採用 **「規則判斷，LLM 解釋」** 的混合式架構。由領域知識規則引擎負責時空對齊與數值門檻判定（降雨、UV、空品、熱舒適），大型語言模型（LLM）負責自然語言需求解析與建議解釋。
* **E. Experiments (實驗與評估)**：設計 Baseline A（純官方數據）、Baseline B（固定規則+模板）與 Proposed（規則+偏好+LLM）三組比較，並在多站跨鄉鎮、高降雨/高 UV、同 AQI 但不同主污染物等 6 大情境下進行測試。
* **F. Findings (預期成果與發現)**：預期能顯著降低跨平台查詢負擔，提升行前建議的個人相關性、可理解性、實用性與可追溯性。

### **I. Introduction（緒論）**

* **G. General (現況)**：中央氣象署與環境部提供豐富的氣象與空品開放資料，具備完善的資料基礎。
* **H. However (挑戰)**：數據獲取不等於決策形成；通用預報無法回應個體對冷熱感、防曬重視度及空品敏感度的差異，使用者仍需負擔額外的資訊解讀成本。
* **I. In literature (文獻解法)**：既有研究涵蓋 Weather Agent 對話查詢、MCP 串接空品、 Instructor-Worker 多代理人健康建議、Profile/Memory 推薦架構、室內熱舒適模型 及 WMO 影響導向預報。
* **J. Judgement (SWOT / 評析既有方法缺點)**：
  * **優點**：驗證了 LLM 對話與工具呼叫整合環境資料的潛力。
  * **限制**：室內模型無法直接外推戶外；語意相似度不等於健康效益；缺乏同時整合多源資料、個人偏好與具備可追溯性的完整系統驗證。
* **K. Keypoint (設計精神與 Novelty)**：強調 **「資料優先、健康與舒適分離、建議可追溯、資料不可編造」** 的核心原則，以混合架構確保數值判定精準且文字親切易懂。
* **L. List the organization (文章結構)**：依序介紹相關研究脈絡、系統混合架構設計、資料對齊策略、虛擬碼實作細節及多維度評估實驗設計。

### **III. Proposed Scheme（系統設計與架構）**

* **PA. Aim (目標)**：針對台灣境內多站行程，產出符合地點、時段、活動與個人偏好的可追溯行前準備建議。
* **PB. Based on (背景基底)**：基於中央氣象署鄉鎮預報與環境部 AQI/空品預報開放資料。
* **PC. Cure/Cause (解法與運作原因)**：採用 **「規則處理判斷，LLM 處理理解與解釋」** 的分工，避免 LLM 自行編造數值或修改優先級。
* **PD. Design (系統架構圖與模組)**：包含 11 個核心模組：①UI、②行程解析、③地點時段標準化、④帳號偏好記憶管理、⑤資料取得、⑥資料品質與時空對齊、⑦規則決策引擎、⑧行程建議彙整器、⑨LLM 解釋與追問、⑩結果與限制呈現、⑪行後問卷與偏好更新。
* **PE. Paper element (系統關鍵資料模型)**：包含 `UserProfile`（偏好）、`ItinerarySegment`（行程段）、`EnvironmentalSnapshot`（環境快照）、`SegmentDecision`（單站決策）、`TripRecommendation`（行程建議）及 `FeedbackRecord`（回饋紀錄）。
* **PF. Formulation / Foundation (功能與決策規則)**：具備四大領域規則：降雨準備、紫外線防護、空品防護（考量主要污染物）、冷熱舒適（結合 UTCI/溫濕度與偏好），並配置資料品質旗標。
* **PG. Graph (架構與流程圖)**：包含系統模組架構圖與使用者情境步驟式流程圖。
* **PH. How (實現方式)**：每站獨立對齊氣象/空品時空資料，經規則引擎產出結構化判定，優先排定健康防護再排舒適建議，最後交由 LLM 生成摘要並解答「為什麼」。
* **PI. Implementation / Interaction / Pseudo code (虛擬碼與互動流程)**：演算法 `Algorithm 1: Personalized Weather Anchor Agent`（步驟 01 至 35）明確規範資料校驗、對齊、規則評估與 LLM 說明生成流程。
* **PJ. Jump to an example (使用範例)**：示範一日多站行程（09:00–12:00 臺中南區步行上課、14:00–17:00 彰化市戶外活動、19:00–21:00 臺中南區騎車返家），展示各站獨立環境數據與個人條件輸出結果。
* **PK. Key points contribution (核心貢獻)**：環境數據轉行動、健康與舒適防護分離、預報不確定性透明揭露、建議依據可追溯。
* **PL. Later simulation (後續評估準備)**：決策過程保存 `ruleId` 與輸入證據 `evidence`，支援後續重現性驗證與實驗測試。
* **PM. Math proof / Logic (邏輯判斷模型)**：引入帶傘決策期望成本模型：
  \\[p \times rL > C\\]
  （其中 \\(p\\) 為遇雨機率、\\(C\\) 為帶傘成本、\\(L\\) 為未帶傘損失、\\(r\\) 為可避免損失比例），用以解釋個人化帶傘門檻的理性決策概念。

### **IV. Simulation / Experiments（實驗與評估）**

* **Q. Quality and Quantity (評估指標)**：
  * **正確性**：建議可重現性。
  * **完整性**：重要提醒遺漏率、資料限制揭露率。
  * **個人化**：符合度與實用性評分。
  * **可理解性**：使用者能否說出站點、時段與原因。
  * **系統性**：API 成功率、資料過期處理率、回應時間。
* **R. Related method to compare (比較基準)**：
  * **Baseline A**：僅顯示官方天氣與 AQI 原始數值。
  * **Baseline B**：固定規則 + 固定文字模板。
  * **Proposed**：規則引擎 + 個人偏好 + LLM 說明（本專題方法）。
* **S. Simulation Setup (測試情境設定)**：設計 6 大測試情境：跨鄉鎮多站行程、高降雨機率且不願帶傘、高 UV 長時間戶外、同 AQI 但主污染物不同、即時與隔日預報切換、資料缺漏/過期/超出範圍。
* **T. Tuning parameters (參數調校)**：輸入不同的個人偏好參數（怕熱/怕冷、防曬重視度、空品敏感度、雨天耐受度）與戶外暴露等級。
* **U. Useful results (預期實驗結果)**：預期 Proposed 方法在個人化符合度與可理解性上顯著優於基線，且能維持重要健康提醒零遺漏。
* **V. Verify the effectiveness (驗證有效性)**：透過功能測試與使用者問卷回饋，驗證系統資訊整合效益、建議合理性與操作便利性。

---

### **V. Conclusion（結論）**

* **W. What proposed (系統總結)**：成功規劃並設計出一套整合官方氣象/空品資料與個人偏好的 AirGuard AI Agent 系統。
* **X. eXcel (專精情境與優勢)**：專精於台灣日常多站行程的行前準備決策，結合「規則引擎之嚴謹可追溯」與「LLM 自然語言之易懂解釋」雙重優勢。
* **Y. Yields (成果產出)**：完成統一資訊介面、個人偏好管理、混合決策架構及完整評估實驗設計。
* **Z. Zen (結論與未來展望)**：實現從「知道天氣如何」到「知道自己該如何準備」的轉變。未來可持續深化行後回饋之偏好自動學習機制與大規模使用者實測。
